项目纯自用、开源、非商业化。CipherTalk-Backup 先作为独立读取端使用。若后续需要复制或修改其源码，再核对对应模块的许可及开源分发要求。

### 实施顺序

1. 构建并验证本机 CipherTalk-Backup 的独立 CLI。用 JSON 模式检查连接，列出会话并查询测试群。验证当前微信版本能读取新消息，以及数据能否提供稳定的群 ID、消息 ID、发送者、时间和正文。
2. 在 wechat-bot 定义读取适配器和统一消息格式。首版按群 ID 轮询白名单，持久化增量游标和去重键；首次启动从当前进度开始监听，历史查询单独用于统计。
3. 配置「群 ID → 关键字 → 处理函数」。先用本地注册表做一条示例指令，处理函数接收消息与只读查询能力，返回回复内容。
4. 将结果写入本地待发送记录，保存目标群 ID、显示名、触发消息 ID、正文和生成时间。验收时确认测试群的新指令只生成一条记录，重启后不会重复生成，其他群的相同指令不会触发。

### 后续回复类型与定位

- **文本、图片、TXT 和 PDF**。文本保存正文，图片和文件保存本地路径。
- **网页分享**。待发送记录保存 URL 和目标群。发送端先在微信内打开链接，再用页面的转发功能分享到目标群，验收以群内实际收到的分享内容为准。链接打不开或页面无法转发时，记录失败原因。
- **引用**。默认关闭。开启时必须指定一条目标群内的消息。引用触发消息时直接使用事件里的群 ID 和消息 ID；引用其他历史消息时，按群 ID 限定范围，再用发送者、时间段、关键词筛选候选。候选多条时由调用者选定，最终保存消息 ID，并保留发送者、时间和文本摘要供手机端定位。待发送记录支持引用信息，实际引用操作取决于手机端能否定位该原消息。
- **@ 群成员**。待发送记录可带一组目标群成员。优先保存可取得的稳定成员 ID，并保留群内显示名；同名时需要确认具体成员。发送端通过微信的群成员选择界面完成真正的 @。

后续实测需要分别确认网页能否从微信内转发、数据库中的原消息能否在手机界面唯一定位，以及群成员 ID 能否映射到微信的 @ 选择项。

### HTTP 回调接入

1. 在 Web 的「关键词规则」中选择群 ID，填入整条匹配的关键词，处理函数选「HTTP 回调」，填写接收服务的 HTTP(S) URL，然后启动监听。
2. 服务收到 POST，Content-Type 为 application/json。事件包含 version、group_id、message_id、sender_id、timestamp_ms 和 text。例如：

   ```json
   {"version":1,"group_id":"example@chatroom","message_id":"message_0:123","sender_id":"wxid_example","timestamp_ms":1794000000000,"text":"测试"}
   ```

3. 返回 HTTP 204 表示处理成功且无需回复。要生成待发送任务，返回 HTTP 200 和如下 JSON：

   ```json
   {"content":{"type":"text","text":"测试成功"}}
   ```

4. content.type 也可为 image、txt、pdf（提供手机执行端可取得的本地 path），或 webpage（提供 url）。可选 quote 接受 message_id、sender_id、timestamp_ms、excerpt，可选 mentions 是由 member_id 和 display_name 组成的数组。协议实现见 server/reply.py。
5. 接收端应在 10 秒内响应。失败后可以在 Web 重试，同一投递的 Idempotency-Key 保持不变。接收端应按该键去重，以处理首次请求已执行但响应丢失的情况。记录会显示处理状态、错误类别和生成的任务。

- 控制台新增 SQLCipher 手动探测，可填写数据库目录、账号和密钥，已用本机库验证能找到指定测试群。表单只做探测；后台使用已有账号设置或 MIYU_DB_PATH、MIYU_WXID、MIYU_KEY_HEX 环境变量。前端构建和加密库回归通过。

- Web 规则支持试跑，显示关键词匹配和本地插件回复。HTTP 规则试跑只检查匹配，不投递请求或写入待发送记录。已验证匹配、未匹配及 HTTP 试跑，前端构建通过。

- HTTP 回调失败记录现在区分响应状态码、连接或读取失败、协议校验失败和响应过大。已验证 503 会显示明确状态码，诊断不包含 URL、消息正文或响应正文。
